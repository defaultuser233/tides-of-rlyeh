### P0-1　单发武器开完第一枪就彻底哑火

**可信度：`[已复核]`**

**定位**
- `src/weapon.rs:616-627`（`Arsenal::wants_fire`）
- `src/main.rs:1146`（唯一的调用门）
- `src/main.rs:415`（`fire_player_shot` 内部的调用点）
- `src/main.rs:1172`（`game.arsenal.update(dt)`）
- 相关枚举：`src/weapon.rs:81-84`、武器定义 `src/weapon.rs:168/245/271`

**现状代码**

```rust
// src/weapon.rs:615-627
/// Feed the trigger state; returns true on the frames a shot should happen.
pub fn wants_fire(&mut self, held: bool) -> bool {
    let pressed = held && !self.trigger_latch;
    self.trigger_latch = held;          // <-- 只在被调用时写，而被调用时 held 恒为 true
    let mode = self.active_weapon().mode();
    match mode {
        FireMode::Auto => held,
        FireMode::Single => pressed,
        FireMode::Burst => pressed || held,
    }
}
```

```rust
// src/main.rs:1146-1148
if held || pressed {
    if melee || game.arsenal.active_weapon().stats().infinite_ammo {
        fire_player_shot(game, audio, pressed, held);   // -> arsenal.wants_fire(held)
```

**根因**

`wants_fire` 唯一的调用路径是 `main.rs:1146` 里那个 `if held || pressed` 分支 → `fire_player_shot`（`main.rs:415`）。
该分支只在按键按下时进入，因此 `wants_fire` **永远只会收到 `held == true`**，`self.trigger_latch = held` 一旦置真就再也回不到 `false`。

于是：
- 第一枪：`trigger_latch == false` → `pressed == true` → 正常发射。
- 之后每一帧：`pressed = held && !true = false` → `FireMode::Single => pressed` 恒为 `false`。
- 松开按键时 `wants_fire` 根本不被调用，闩锁保持 `true`。

**后果**：`weapon.rs:168 / 245 / 271` 定义了 **手枪、霰弹枪、狙击枪、匕首** 的 `fire_modes` 均为 `SEMI`（`weapon.rs:81`），这 4 把武器**每局只能开一枪**，之后完全失效。切换武器无效——`trigger_latch` 只在 `Arsenal::new`（`weapon.rs:509`）初始化，`Arsenal::select` 不重置它。

步枪和冲锋枪默认是 `Auto`，所以能玩——这也解释了为什么之前的测试没发现（README 的验证章节只提到"开了一枪确认弹匣是 30/30"）。

**建议补丁**

把闩锁的维护从"开火路径"移到"每帧必跑的 `update`"。

```rust
// ---- src/weapon.rs ----

/// 只读取状态，不再修改。
pub fn wants_fire(&self, held: bool) -> bool {
    let pressed = held && !self.trigger_latch;
    match self.active_weapon().mode() {
        FireMode::Auto   => held,
        FireMode::Single => pressed,
        FireMode::Burst  => pressed || held,
    }
}

/// 每帧调用一次，`held` 为扳机当前是否按下。
pub fn update(&mut self, dt: f32, held: bool) {
    self.trigger_latch = held;                        // <-- 新增：每帧都写
    self.switch_t = (self.switch_t - dt).max(0.0);
    for w in self.slots.iter_mut().flatten() {
        w.update(dt);
    }
}
```

```rust
// ---- src/main.rs:1172 ----
game.arsenal.update(dt, held);        // 原为 game.arsenal.update(dt);
```

**时序说明**：`update` 在开火块之后调用，因此第 N 帧写入的闩锁反映第 N 帧的按键状态，第 N+1 帧的 `wants_fire` 读到正确的"上一帧状态"。按下瞬间仍能正确产生 `pressed == true`。

若 `active_weapon()` 需要 `&mut self` 而无法在 `&self` 方法内调用，改为 `self.active_weapon_ref()` 或直接 `self.slots[self.active]` 的共享借用即可。

**顺带修复（同一处代码）**：`main.rs:1146-1165` 里 `audio.play(...)` 无条件执行，而 `fire_player_shot` 在冷却中/弹匣空时会提前返回——
- 自动武器因此以 `audio.rs` 的限流上限 25 次/秒播放枪声，而真实射速只有 11.4（步枪 0.088 s 间隔）～18 次/秒 → **枪声密度约为实际的 2 倍**，换弹期间也在响。
- 近战分支更严重：`main.rs:1149-1151` 的 `if melee { audio.play(Sfx::HitFlesh); }` 在**按住左键的每一帧**都播放，即 40 次/秒的刺中音，无论是否真的挥砍、是否命中。

建议让 `fire_player_shot` 返回 `bool`（是否真的开火），只在 `true` 时播放：

```rust
fn fire_player_shot(game: &mut Game, audio: &audio::Audio, pressed: bool, held: bool) -> bool {
    // ... 原有的提前返回处改成 return false; 成功路径末尾 return true;
}
```
```rust
// main.rs 开火块
let fired = fire_player_shot(game, audio, pressed, held);
if fired {
    audio.play(match kind { /* ... */ });
}
```
并删除 `main.rs:1149-1151` 那段（真实命中已经在 `fire_player_shot` 内部播放了 `HitFlesh`）。

**验证**
1. `cargo check` 通过。
2. 进游戏 → 按 `3` 切到手枪 → 连续点击左键 10 次 → **应开出 10 枪**（当前只有 1 枪）。
3. 按 `4` 切到匕首，连续点击 10 次 → 应有 10 次挥砍。

### P0-2　随机数上限只有 0.5，全游戏的随机都错了一半

**可信度：`[已复核]`**

**定位**：`src/util.rs:13-23`

**现状代码**

```rust
pub fn u32(&mut self) -> u32 {
    self.s = self
        .s
        .wrapping_mul(6364136223846793005)
        .wrapping_add(1442695040888963407);
    (self.s >> 33) as u32                     // 只剩 31 位有效数据，最大 2^31-1
}

pub fn f32(&mut self) -> f32 {
    self.u32() as f32 / 4_294_967_295.0       // 却按 32 位（2^32-1）去除
}
```

**根因**

`u64 >> 33` 只保留 31 位，最大值为 `2_147_483_647`；除数却是 `2^32 - 1`。
因此 **`f32()` 的取值区间是 `[0, 0.5)`**，而不是设计意图的 `[0, 1)`。

这个错误不需要看调用点就能推出后果：

| 调用形式 | 设计意图 | 实际行为 |
|---|---|---|
| `chance(p)`，`p < 0.5` | 概率 `p` | 概率 **`2p`** |
| `chance(0.5)` | 50% | **恒为真**（`f32()` 最大 0.49999999988） |
| `range(lo, hi)` | 全区间均匀分布 | 恒落在**区间前半段** |
| `range(0.0, TAU)` | 整圆 | 只有半个圆（`[0, π]`） |
| `signed()` | `[-1, 1]` | `[-1, 0]` |
| `f32().sqrt()`（`cone()` 内） | 均匀圆盘采样 | 半径被压在 0.707 倍以内 |

已知受影响的实际逻辑包括：敌人侧移方向的选择（`chance(0.5)` 恒真 → **所有敌人永远向同一侧移动**）、出生朝向（只覆盖半圈）、各类掉落判定、散布与粒子抖动（一律偏小）。

**建议补丁**

```rust
pub fn u32(&mut self) -> u32 {
    self.s = self
        .s
        .wrapping_mul(6364136223846793005)
        .wrapping_add(1442695040888963407);
    (self.s >> 32) as u32                     // 取高 32 位
}

/// 返回 [0, 1) —— 严格半开区间，避免 `as f32` 舍入到恰好 1.0。
pub fn f32(&mut self) -> f32 {
    (self.u32() >> 8) as f32 / (1u32 << 24) as f32
}
```

**为什么用 `>> 8` 而不是直接除**：`u32 as f32` 会舍入到最近的可表示值，`u32::MAX as f32 == 4294967296.0`，除以 `4294967295.0` 会得到 `1.0000000002`，破坏 `[0,1)` 的契约。取高 24 位后除以 2²⁴ 可以精确表示，结果严格落在 `[0, 1)`。

同样的写法问题也出现在 `src/grenade.rs:292-298`（自带的私有 RNG，`>> 33` 除以 `2_147_483_647.0`，同样会取到 1.0）。它只用于自旋动画，危害较小，建议一并改成 `&mut Rng` 或至少改成除 `2_147_483_648.0`。

**验证**

在 `src/util.rs` 末尾加单元测试（这也是本仓库第一个测试）：


**可信度：`[已复核]`**

**定位**：`src/main.rs:812`（恢复）、`src/main.rs:1140-1145`（重新武装）、`src/main.rs:226-229`（`start()`）、`src/main.rs:946-957`（鼠标基准）

**现状代码**

```rust
for i in 0..3 {
```

```rust
// src/main.rs:1137-1145
// The click that left the menu is still held on the first frame of the
// mission, which used to fire a burst into the wall every time.
if !is_mouse_button_down(MouseButton::Left) {       // <-- 只有这一条重新武装路径
    game.trigger_armed = true;
}
let held = is_mouse_button_down(MouseButton::Left) && game.trigger_armed;
```

**根因（两个独立问题，同源）**

`trigger_armed` 只在 `Game::new`（`main.rs:183`）和 `start()`（`main.rs:229`）里被置 `false`。暂停期间 `simulate` 完全不被调用，因此：

1. **误开火**：点 "RESUME" 的那次左键点击从未经过 `main.rs:1140` 的重新武装判断。恢复后按钮可能仍被按住 → 下一帧 `held == true` → 立即开火。这正是 README 声称已修复的那一类 bug，只是从另一扇门进来。

2. **视角瞬移**：`mouse_ready` 也只在 `start()` 里清零（`main.rs:228`）。覆盖层（Tab/M/J）或暂停打开期间光标被释放且不被重置中心，`last_mouse` 保持旧值。关闭覆盖层的那一帧会**把积攒的全部位移一次性算作转向**——默认灵敏度下最多约 1.6 rad（≈90°）；每次从暂停恢复约 10°。

**建议补丁**

在所有"重新进入 Playing"的切换点补上两行。建议抽一个辅助函数，避免以后再加状态时又漏：

```rust
impl Game {
    /// 回到可操作状态：吞掉切界面时残留的输入。
    fn resume_play(&mut self) {
        self.phase = Phase::Playing;
        self.trigger_armed = false;   // 需要重新松开一次左键才能开火
        self.mouse_ready = false;     // 下一帧重新校准鼠标基准，避免视角跳变
    }
}
```

调用点：
- `src/main.rs:812` → `game.resume_play();`
- 覆盖层关闭处（Tab / M / J 的收尾逻辑）→ 只加 `game.mouse_ready = false;`（那里不涉及开火）

`mouse_ready == false` 时 `main.rs:948-951` 会把 `last_mouse` 重置为当前光标位置，即"以现在的鼠标位置为基准"，正是所需行为。

**验证**
1. 进游戏 → 按 `Esc` → 用鼠标点击 "RESUME" → **不应有枪声、不应消耗弹药**。
2. 按 `Esc` → 点 "RESUME"，同时把光标停在屏幕角落 → 恢复后视角**不应瞬移**。
3. 打开 `Tab`，把鼠标移到屏幕边缘，关掉 `Tab` → 视角不应跳变。
4. 反复开关 5 次，确认没有累积漂移。

### P0-5　鼠标转盘（手雷 / 医疗）永远选不中

**可信度：`[已复核]`（时序细节见"残余不确定性"）**

**定位**：`src/main.rs:954`（每帧重置光标）、`src/main.rs:1448-1466`（扇区判定）、调用点 `src/main.rs:1083` / `1107` / `1571` / `1592`

**现状代码**

```rust
// src/main.rs:954 —— 位于 simulate() 内，每帧执行
if let Some(landed) = pointer::recenter(cur) { game.last_mouse = landed; }
```

```rust
// src/main.rs:1448-1460
fn wheel_selection(n: usize) -> Option<usize> {
    if n == 0 { return None; }
    let (mx, my) = mouse_position();
    let c = vec2(screen_width() * 0.5, screen_height() * 0.5);
    let d = vec2(mx, my) - c;
    if d.length() < 40.0 { return None; }        // <-- 死区，光标永远不会离中心这么远
    // ...
}
```

**根因**

`pointer::recenter` 每帧用 `SetCursorPos` / `XWarpPointer` 把光标拉回窗口中心（这是鼠标视角能工作的前提，见 README 的说明）。

按住 `G` / `V` 时 `simulate` 照常运行，所以中心化也照常发生。于是 `mouse_position()` 返回的永远是"中心 + 上一帧的位移量"，`d.length()` 通常只有几像素，**永远过不了 40 px 死区**。`wheel_selection` 恒返回 `None`，`unwrap_or(w.selected)`（`main.rs:1571` / `1592`）就一直停在初始选项。

**后果**：烟雾弹和医疗物品实际上选不出来，与 README 第 77-79 行"按住 `G`，用鼠标瞄准，松开投掷"的描述不符。

**建议补丁**

思路：转盘打开期间**不要中心化光标**，改用游戏自己累积的视角增量来决定扇区。

```rust
// src/main.rs:954 附近 —— 转盘打开时跳过中心化
let wheel_open = game.wheel.is_some() || game.med_wheel.is_some();
if !wheel_open {
    if let Some(landed) = pointer::recenter(cur) { game.last_mouse = landed; }
} else if let Some(landed) = pointer::recenter(cur) {
    game.last_mouse = landed;           // 仍需重置基准，否则关掉转盘时会瞬移
    game.wheel_aim += cur - landed;      // 累加到转盘专用偏移（按需 rename 字段）
}
```

然后把 `wheel_selection(n)` 改成接收这个累积偏移而不是读 `mouse_position()`：

```rust
fn wheel_selection(n: usize, aim: Vec2) -> Option<usize> {
    if n == 0 { return None; }
    if aim.length() < 40.0 { return None; }
    // 其余不变，但用 aim 代替 d
}
```

转盘打开时（`main.rs:1081-1120` 附近）把 `game.wheel_aim` 清零；关闭时也清零。

> 若不想引入新字段，最小改法：转盘打开时用 `game.last_mouse` 与当前 `mouse_position()` 的**累积和**代替绝对位置。但引入一个专用 `Vec2` 字段最清晰。

**残余不确定性**：Windows 会合并待处理的 `WM_MOUSEMOVE`，因此极少见情况下一次极快的甩动（>2400 px/s）可能在单帧内累积超过 40 px 从而使转盘"偶尔响应"。这不影响结论——无论哪种情况，当前的转盘都基本不可用。

**验证**
1. 进游戏，按 `G` 按住不放，鼠标向左右各划过一段距离 → 高亮扇区应跟随移动。
2. 松开 → 应投出高亮的那种手雷（当前恒为列表第一项）。
3. 按 `V` 同样验证医疗轮。
4. 关掉转盘后立即移动鼠标 → 视角**不应**跳变（验证基准重置仍然生效）。

### P1-1　碰撞只有终点检测，没有扫掠；安全性寄托在调用方的一个魔法数字上

**可信度：`[已复核]`（`resolve_axis` 与 `player.rs` 的截断）；隧穿结论 `[静态定位]`**

**定位**：`src/level.rs:87-94`（`resolve_axis`）、`src/player.rs:443-448`（玩家的 0.85 m 截断）、`src/enemy.rs:891-899`（敌人路径，无截断）

```rust
// src/level.rs:87-94 —— 注释说"扫描"，实际只测终点
// Sweep: test the body at its destination, not at its origin.
let mut probe = pos;
match axis { 0 => probe.x = moved, 1 => probe.y = moved, _ => probe.z = moved }
let b = body(probe, radius, height);
```

```rust
// src/player.rs:443-448
self.vel.y = (self.vel.y - GRAVITY * dt).max(-MAX_FALL);
let mut step = self.vel * dt;
if step.length() > 0.85 { step = step.normalize() * 0.85; }
```

**问题一：帧率依赖**

那个 0.85 截断是唯一的防穿墙措施，但它是施加在**位移**上的，而 `vel` 继续增长。于是有效终端速度变成 `0.85 / dt`：

| 帧率 | 实际终端下落速度 |
|---:|---:|
| 144 Hz | 60 m/s（`MAX_FALL` 生效） |
| 60 Hz | 51 m/s |
| 30 Hz | 25 m/s |
| 20 Hz | 17 m/s |

同一段落差在不同机器上用时不同。而且截断作用在**向量长度**上——下落时水平位移也会被一起缩放，20 FPS 下冲刺下落时水平位移只有正常值的 36%。另外 `landing`（`player.rs:466-470`）报告的是**未截断**的速度，视觉/音效与位移不一致。

**问题二：隧穿（潜伏）**

玩家横向安全性目前只剩 0.10 m 余量：地图中最薄的实体是 0.15 m（`src/maps.rs:184-187` 的栏杆），需要 `step > 0.15 + 2×0.40 = 0.95` 才会穿过去，而截断是 0.85。

敌人路径**没有这个截断**（`src/enemy.rs:891-899` 直接传 `self.vel * dt`，重力上限 60 m/s），`dt = 0.05` 时单帧位移可达 3.0 m，远超 0.70/0.72 m 高敌人的容差。当前地图没有 78 m 的落差所以打不到终端速度，**属于"改一次地图就会踩中"的隐患**。

**建议补丁**：把安全性做成碰撞函数的内在属性，而不是调用方的义务。

```rust
// src/level.rs —— 在 move_and_collide 内部按步长细分
const MAX_SUBSTEP: f32 = 0.20;   // 应 < 地图最薄实体厚度与最小半径

pub fn move_and_collide(&self, pos: Vec3, radius: f32, height: f32, delta: Vec3) -> (Vec3, Collision) {
    let steps = (delta.length() / MAX_SUBSTEP).ceil().max(1.0) as usize;
    let sub = delta / steps as f32;
    let mut p = pos;
    let mut col = Collision::default();
    for _ in 0..steps {
        let (np, c) = self.resolve_xz(p, radius, height, sub);
        p = np;
        col.ground |= c.ground;
        col.ceiling |= c.ceiling;
    }
    (p, col)
}
```

然后**删除** `player.rs:446-448` 的截断。这样 `MAX_FALL` 与 `SPRINT_SPEED` 重新变得有意义，敌人也自动继承同样的保护。

另外，建议在 `resolve_axis` 末尾加一句断言，把静默失败变成响亮的失败：

```rust
debug_assert!(
    !self.solids.iter().any(|s| s.overlaps(&body(pos, radius, height))),
    "碰撞解析后仍与实体重叠: pos={pos:?}"
);
```

**验证**：在 30 FPS 与 144 FPS 下分别从同一高度跳下，落地时间应一致；把窗口拖拽到极低帧率，确认不会穿出场景。

**定位**：`src/level.rs:406`（阻挡判定）vs `src/level.rs:9`（`STEP_HEIGHT = 0.62`）vs `src/enemy.rs:883-899`（移动）

### P1-3　无人机的碰撞箱与模型错位

**可信度：`[静态定位]`——建议先跑一次确认**

**定位**：`src/enemy.rs:330-374`（`build_drone` 的局部坐标）、`src/enemy.rs:729-738`（`body_aabb`）、`src/enemy.rs:742-757`（`head_y` / `eye`）、`src/combat.rs:27-33`（命中判定）

**问题**

无人机模型建立在局部 `y ∈ [-0.62r, +0.35r]`（`r = 0.38` → `[-0.236, +0.133]`），但：
- `body_aabb()` 是 `[pos.y, pos.y + 0.70]`；
- `head_y()`（飞行单位）返回 `pos.y + height * 0.45 = pos.y + 0.315`；
- `eye()` 返回 `pos.y + height * 0.5 = pos.y + 0.35`。

后果：
1. **打不中**：模型的下半部（大约 2/3 的可见机身）位于碰撞箱**下方**，对着它开枪会完全落空。
2. **全是爆头**：碰撞箱上半部（模型上方约 0.57 m 的空气）全部满足 `y > head_y()`（`combat.rs:33`），每一枪都是爆头倍率。
3. 枪口火光从模型上方约 0.22 m 的空中冒出。

人形 / 触手 / 幼体的模型都规范地占 `[0, h]`，**只有飞行单位不一致**。

**建议补丁**（二选一，任选其一即可，关键是"模型与箱子用同一套约定"）

- 方案 A（改箱子，改动最小）：让 `body_aabb()` 对 `flying` 返回以 `pos` 为中心的盒体。
  ```rust
  pub fn body_aabb(&self) -> Aabb {
      if self.flying {
          Aabb::new(
              vec3(self.pos.x - self.radius, self.pos.y - self.height * 0.62, self.pos.z - self.radius),
              vec3(self.pos.x + self.radius, self.pos.y + self.height * 0.35, self.pos.z + self.radius),
          )
      } else { /* 原有逻辑不变 */ }
  }
  ```
  同时把 `head_y()` / `eye()` 的飞行分支也按同一基准调整。
- 方案 B（改模型）：在 `mesh()` 里给飞行单位加 `+ height * 0.62` 的 y 平移，让模型也占 `[0, h]`。

**验证**：进任务 5（CITADEL 有无人机），对着无人机的**可见机身下半部**开枪 → 应能命中；观察伤害数字，确认不再全是爆头。

## 8. 边界与约束（给执行者）

1. **不要顺手重构无关代码。** 本报告列出了大量的结构问题（P2-7），但它们应当**单独提交**，不要和 P0 的功能修复混在一起——P0 的修复需要能一个一个地回滚和验证。
2. **不要引入新依赖。** 项目刻意保持最小依赖集（只有 macroquad），P0/P1 的所有修复都不需要新 crate。如果确实需要，先用 `cargo add <crate> --dry-run` 确认最新版本，并在提交信息里说明理由。
3. **不要改动游戏平衡数值**，除非任务明确要求（P1-5 的 `total_enemies`、P1-6 的 `wave` 是例外）。`campaign.rs` 里的伤害、射速、敌人权重都是刻意调过的。
4. **保持双语。** 任何新增的用户可见文案都必须同时补中文和英文——`i18n.rs:46-64` 的 `define_strings!` 宏会强制这一点，缺一个就编译不过。这是设计上的优点，不要去绕过它。
5. **保留 `sound` feature 的双配置可编译性。** 每次改动音频相关代码后都要跑 `cargo check --no-default-features`，因为交叉编译的 Linux 版本依赖它。
6. **`clippy::approx_constant` 是 deny 级的。** 在 `cargo fmt` 之后、clippy 通过之前，`cargo clippy` 不是一个可用的验证门槛——先修 `hud.rs:374-377`。
7. **改动 `resolve_axis` / `move_and_collide`（P1-1）时要格外小心**：这是整个游戏最核心的不变量所在，改完必须在低帧率下手动跑一遍并确认 `debug_assert!` 不触发。
8. **提交粒度**：一个 P0/P1 编号 = 一个提交，提交信息里带上编号（例如 `fix(P0-1): refresh trigger latch every frame so Semi weapons keep firing`）。

## 9. 附录：值得保留的设计（不要在重构中弄丢）

1. **手雷物理**（`grenade.rs:303-364`）：Minkowski 膨胀 AABB + 自适应子步扫掠 + "接触但终点不重叠就不算命中"的规则。弹速再高也不穿墙，弹性系数只乘不加，不会越弹越猛，`fuse` 在 `resting` 之外递减所以静止的手雷照样会炸。注释写清了每条规则为什么存在。
2. **武器的 2D 投影**（`viewmodel.rs:943/1128-1145`）：使用相机自己的 FOV 约定（弧度、宽高比正确抵消），按三角形整体丢弃近平面/非有限顶点。`w <= 0` 除零这一类经典 bug 在结构上不可能发生。
3. **指针重定位**（`pointer.rs`）：位移取整一次后回传给基准，避免亚像素残差累积成漂移；X11 侧全程 `dlopen` + 空指针检查，没有 panic 路径。P0-4 的修复要保持这个性质。
4. **`i18n.rs` 的编译期双语保障**：缺一条翻译就编译不过，语言热切换无需重启。它的问题是**有 25 个键从未被引用**（即功能承诺了但没做），不是缺翻译。
5. **`enemy.rs:759-776` 的死亡簿记**：单一 `death_t` 时钟驱动淡出、下沉、`is_removable()` 与绘制跳过，阈值彼此一致；`take_damage` 的提前返回让击杀计分幂等。
6. **`hud.rs` 的分辨率无关绘制层**：统一的 `Ui` 缩放、`font_px` 钳制 `u16` 转换、`sane`/`clamp_span`/`map_ppu` 让非有限几何不可能被绘制、所有变长文本都过 `fit()`。P2-6 里关于 `draw_sanity_bar` 和 `Ui::scale` 上限的两条是这层仅有的例外。
7. **`level.rs:164-180` 的台阶抬升是有门控的**：`point_free(lifted)` 加上 `support_height` 被夹在 `(pos.y + 0.004, pos.y + step_height + 0.001)` 区间内，不可能把你瞬移到脚下有东西的表面上。
